## Editions

WinMux постачається у двох редакціях, з єдиним базовим engine:

### 1. WinMux CLI (винmux-cli-setup.exe / .zip)
- **Розмір:** ~280 МБ (компактний QEMU + rootfs + бінарники, без UI)
- **Що всередині:** `winmux.exe` (контролер) + `qemu/` + `rootfs/` (frozen.qcow2 + vmlinuz)
- **UI:** жодного власного. Користувач керує через PowerShell/CMD: `winmux start`, `winmux ssh`, `winmux stop`
- **Цільова аудиторія:** DevOps, Windows Server admins, скриптові сценарії, CI/CD pipelines, headless installations
- **Use cases:** Запуск Linux-середовища на віддалених серверах через RDP/WinRM, інтеграція з automation, AI-агенти на cron/scheduler

### 2. WinMux Desktop (winmux-desktop-setup.exe / .zip)
- **Розмір:** ~330 МБ (CLI + Tauri UI + WebView2 dependencies)
- **Що всередині:** все з CLI + `winmux-desktop.exe` (Tauri) + `webview2-bootstrap`
- **UI:** Власний термінал на Tauri 2 + xterm.js: вкладки, теми, drag-and-drop, settings, Mica/Acrylic
- **Цільова аудиторія:** Розробники на Windows, AI-користувачі (claude_code), все що потребує візуального терміналу
- **Use cases:** Заміна WSL для щоденного використання, drag-and-drop файлів/скріншотів у `claude`, кілька проектів одночасно

### Спільне для обох
- Один двигун: контролер на Rust + QEMU + Ubuntu rootfs
- Один config format (`winmux.toml`)
- Спільні файли (можна встановити обидві редакції паралельно — вони шерять `%LOCALAPPDATA%\WinMux\rootfs\`)
- Однаковий API/протокол (Desktop використовує той самий контролер що й CLI)

## 1. Загальні відомості

### 1.1. Назва проекту
**WinMux** — портативне Linux-середовище для Windows.

### 1.2. Коротка мета
Дати користувачам Windows (десктоп або сервер) повноцінне Linux-середовище в одному `.exe` файлі — без WSL, без Hyper-V, без перезавантажень, без прав адміністратора, з нативним відчуттям інтеграції (спільна ФС, спільний `localhost`, drag-and-drop).

### 1.3. Унікальна цінність
Існуючі рішення мають слабкі місця:

| Інструмент | Проблема |
|------------|----------|
| **WSL2** | Потребує Hyper-V → права адміна, перезавантаження, не працює на багатьох Windows Server без додаткових ролей |
| **Cygwin / MSYS2 / Git Bash** | Не справжній Linux: інші бінарники, проблеми з `node-gyp`, нативними npm-модулями, Docker CLI тощо |
| **Docker Desktop** | Сам потребує WSL2 або Hyper-V |
| **PowerShell + Windows-нативний `claude` CLI** | LLM "мислять" у POSIX-парадигмі: `bash`, `grep`, `sed`, `curl`, `jq`. На PowerShell агент часто пише непрацюючі команди, помиляється з лапками, шляхами тощо |

WinMux усуває ці проблеми: **справжній Linux-userland** (glibc + Ubuntu пакети) у user-space віртуалізації, який виглядає для користувача як рідний термінал Windows.

### 1.4. Робочі назви файлів і шляхів
- Бінарник: `winmux.exe`
- Дані за замовчуванням: `%LOCALAPPDATA%\WinMux\` (без прав адміна)
- Конфіг користувача: `%APPDATA%\WinMux\config.toml`
- Образ ОС: `%LOCALAPPDATA%\WinMux\rootfs\base.qcow2` + overlay `user.qcow2`
- Логи: `%LOCALAPPDATA%\WinMux\logs\`

## 2. Контекст і проблематика

### 2.1. Чому це з’явилося
Конкретний драйвер — робота **AI-агентів типу `claude_code`** на віддалених Windows-серверах. Сценарій:

> Адмін підключається через RDP до Windows Server, хоче запустити `claude` для автоматизації задач (рефакторинг, скрипти, аналіз логів, генерація конфігів). На сервері немає WSL і не буде — це продакшн-сервер, де ставити Hyper-V не можна. Адмін має максимум — користувацькі права.

Сьогодні такий адмін має варіанти:
1. Працювати через PowerShell з обрізаним функціоналом → агент часто помиляється.
2. Підняти SSH-тунель до іншої Linux-машини → потрібна окрема інфраструктура.
3. Поставити Cygwin → ламається на нативних npm-модулях, Docker, Python з C-розширеннями.

**WinMux — це варіант #4: повноцінний Linux прямо тут, без жодної підготовки сервера.**

### 2.2. Чому WSL не вирішує задачу
- Hyper-V вимагає прав адміна та перезавантаження.
- На Windows Server WSL поставити можна, але це окрема серверна роль, не завжди погоджена з безпекою.
- WSL2 використовує власний Linux kernel у Hyper-V — додаткові 1-2 ГБ RAM завжди.
- Інтеграція з UI скромна — стандартний Windows Terminal, без drag-and-drop файлів/скрінів в стилі веб-Claude.

### 2.3. Чому Termux як натхнення
Termux на Android тому і простий, що Android = Linux kernel. WinMux НЕ зможе бути таким простим (Windows ≠ Linux), але може бути таким **на вигляд для користувача**: один файл, без налаштування, миттєвий запуск.

## 3. Цільова аудиторія та сценарії використання

### 3.1. Аудиторія
1. **DevOps / SRE на Windows** — потрібен Linux для скриптів, без можливості ставити WSL.
2. **AI-користувачі (`claude_code`, інші CLI-агенти)** — потрібне POSIX-середовище для адекватної роботи LLM.
3. **Розробники-Linux на Windows-машинах** — простіша альтернатива WSL.
4. **Адміни віддалених Windows Server (через RDP)** — дати команді інструмент без переналаштування серверів.
5. **Студенти / освіта** — швидко спробувати Linux без двойного бута і VM.

### 3.2. Ключові сценарії (User Stories)

**US-1.** Як адмін, я завантажую `winmux.exe`, кладу на Робочий стіл, два кліки — і за 3 секунди маю термінал з `bash`, `git`, `node`, `python3`. Без жодних запитів адміна.

**US-2.** Як AI-користувач, я запускаю WinMux, пишу `claude`, ввожу свій ANTHROPIC_API_KEY (або він автопідхопився з Windows env), і агент працює як у нативному Linux — `grep`, `sed`, `find` працюють очікувано.

**US-3.** Як розробник, я в Windows Explorer натискаю правою кнопкою на папку проекту → "Open in WinMux" → відкривається термінал, де `pwd` показує `/workspace` (та сама папка, видима з обох сторін).

**US-4.** Як адмін на віддаленому сервері, я запускаю довгу задачу в `claude`, RDP-сесія обривається. При повторному вході відкриваю WinMux — побачу, що Claude дописав код за час моєї відсутності.

**US-5.** Як користувач, я перетягую PNG-скріншот прямо в вікно WinMux → файл копіюється в `/workspace/.winmux-drops/screenshot-2026-04-24-153012.png` і шлях вставляється в командний рядок (готовий до передачі в `claude`).

**US-6.** Як розробник, я в Linux запускаю `python -m http.server 8080`. Через 1-2 секунди в Windows-браузері відкриваю `http://localhost:8080` — працює без жодних додаткових налаштувань.

**US-7.** Як користувач кількох серверів, я зберігаю профілі сесій ("PROD-01", "DEV-02") з різними API-ключами та дефолтними папками — переключаюся одним кліком.

## 4. Цілі та некелі проекту

### 4.1. Цілі (in scope)
- ✅ Повноцінний Linux userland (glibc, apt) у user-space.
- ✅ Запуск без прав адміністратора, без Hyper-V, без перезавантажень.
- ✅ Спільна файлова система Windows ↔ Linux.
- ✅ Спільний `localhost` (автопрокидання портів обох напрямків).
- ✅ Власний термінал з вкладками, темами, drag-and-drop.
- ✅ Передвстановлений `claude` CLI та інструменти для AI-роботи.
- ✅ Persistence через `tmux` — переживає закриття вікна терміналу.

### 4.2. Некелі (out of scope, як мінімум для v1)
- ❌ GUI-додатки Linux (X11, Wayland, GTK-програми) — лише термінал.
- ❌ Підтримка GPU passthrough (CUDA/ROCm всередині гостя).
- ❌ Систем-демонізація (запуск як Windows Service на старті ОС).
- ❌ Підтримка ARM Windows (тільки x86_64 у v1).
- ❌ Multi-user (кілька Windows-користувачів одночасно мають окремі інстанси).
- ❌ Шифрування образу гостьової ОС (можна додати в v2).

## 5. Архітектура системи

### 5.1. Високорівнева схема

```
┌────────────────────────────────────────────────────────────────┐
│                         WINDOWS HOST                            │
│                                                                  │
│  ┌──────────────────────┐      ┌──────────────────────────┐    │
│  │   Frontend (Tauri)   │◄────►│  Controller (Rust)       │    │
│  │  - xterm.js          │ IPC  │  - QEMU lifecycle        │    │
│  │  - Drag&Drop UI      │      │  - Port proxy            │    │
│  │  - File explorer     │      │  - Filesystem server     │    │
│  │  - Settings          │      │  - Clipboard sync        │    │
│  └──────────────────────┘      └──────────┬───────────────┘    │
│                                            │                     │
│                                  spawns │  manages              │
│                                            ▼                     │
│                                  ┌──────────────────┐            │
│                                  │  qemu-system-    │            │
│                                  │  x86_64.exe      │            │
│                                  │  (user-mode)     │            │
│                                  └─────────┬────────┘            │
│                                            │                     │
└────────────────────────────────────────────┼─────────────────────┘
                                             │ virtio-{serial, fs, net}
                                             ▼
                       ┌──────────────────────────────────────────┐
                       │          GUEST: Ubuntu Minimal            │
                       │                                            │
                       │  ┌─────────────────────────────────────┐  │
                       │  │  Init (no systemd) → guest-agent    │  │
                       │  │   ↓                                  │  │
                       │  │  /workspace (virtiofs ← Win CWD)    │  │
                       │  │  /c, /d, /e (virtiofs ← Win drives) │  │
                       │  │  Network: SLIRP → host NAT          │  │
                       │  │  Port watcher → notify host         │  │
                       │  │   ↓                                  │  │
                       │  │  bash + tmux + claude + node + ...  │  │
                       │  └─────────────────────────────────────┘  │
                       └──────────────────────────────────────────┘
```

### 5.2. Три шари

| Шар | Мова | Запускається | Відповідає за |
|-----|------|--------------|---------------|
| **Frontend** | Rust + TS (Tauri 2 + xterm.js) | При відкритті вікна | UI, ввід/вивід, drag-and-drop, налаштування |
| **Controller** | Rust | Як дочірній процес від Frontend (або stand-alone tray) | Запуск/контроль QEMU, проксі портів, IPC, синхронізація буфера |
| **Guest Agent** | Rust або Go (статично злінкований) | PID 1 у госту або як service | Прийом команд, моніторинг портів, монтування ФС, проксі IPC |

### 5.3. Потік даних "натиснута клавіша → результат на екрані"
1. Користувач натискає клавішу у вікні Tauri.
2. xterm.js → Rust backend через Tauri-команду.
3. Controller → запис у PTY → через `virtio-serial` (або через TCP-проксі на `vsock`-подібному каналі) → Guest.
4. Guest Agent → запис у відповідний PTY всередині `tmux`-сесії.
5. `bash` обробляє команду → вивід у PTY.
6. Зворотний шлях: Guest Agent читає PTY → IPC → Controller → Frontend → xterm.js → екран.

**Очікувана затримка:** <5 мс на локальній машині, не помітно для людини.

## 8. Гостьова ОС — образ Linux

### 8.1. Дистрибутив
**Ubuntu 24.04 LTS Minimal** (rootfs з cloud-image або вручну зібраний `debootstrap`).

**Чому Ubuntu, а не Alpine:**
- glibc — повна сумісність з npm-нативними модулями (Claude Code тягне `tree-sitter`, `sharp`, інше).
- `apt` — звичніший для більшості користувачів.
- Найбільша кількість готових бінарників в інтернеті.

### 8.2. Розмір
- Базовий rootfs стиснутий: ~150 МБ.
- Розпакований у образі: ~400 МБ.
- Overlay користувача: на старті ~10 МБ, росте з установкою пакетів.

### 8.3. Init-система
**Не systemd.** Замінено на власний легкий init (написаний на Rust) — `winmux-init`.
Він:
1. Монтує `/proc`, `/sys`, `/dev`, віртіофси.
2. Налаштовує мережу (`dhcp` або static на `eth0`).
3. Запускає Guest Agent.
4. Запускає `getty` на серійному порту для tty.
5. Передає керування `tmux` сесії.

**Чому не systemd:** холодний старт скорочується з ~5 с до ~1 с.

### 8.4. Передвстановлені пакети
Базовий шар:
```
bash zsh fish tmux screen
git curl wget jq ripgrep fd-find fzf bat
build-essential gcc g++ make cmake
python3 python3-pip python3-venv pipx
nodejs (v22 LTS) npm pnpm bun
sudo less nano vim
ca-certificates openssl gnupg
openssh-client rsync
htop btop ncdu tree
docker-cli (без daemon — можна вказати на Docker Desktop або зовнішній)
```

AI-шар (опційний рівень, ставиться першим запуском або по запиту):
```
@anthropic-ai/claude-code (npm)
@openai/codex (за бажанням)
ollama (як CLI; daemon — на хості)
litellm
```

### 8.5. Користувач
- Дефолтний користувач: `winmux` (uid 1000).
- Без пароля для `sudo` (бо це user-space VM, ізоляція не від користувача).
- `$HOME = /home/winmux`, persistent через overlay.

### 8.6. Оновлення базового образу
Окремий канал оновлень — `winmux update --rootfs` тягне новий `base.qcow2` з GitHub Releases (або іншого CDN). Overlay користувача не зачіпається.

## 9. Файлова система та спільні папки

### 9.1. Технологія
**Основна: virtiofs** (через `virtiofsd`).
**Fallback: 9p** (для старіших версій QEMU або де virtiofs не запускається).

### 9.2. Mapping
| Windows | Linux | Mode |
|---------|-------|------|
| Поточна папка запуску | `/workspace` | rw |
| `C:\` | `/c/` | rw (опційно) |
| `D:\`, `E:\`, ... | `/d/`, `/e/`, ... | rw (опційно) |
| `%USERPROFILE%` | `/mnt/winhome` | rw |
| `%USERPROFILE%\.ssh` | `/home/winmux/.ssh-host` (потім симлінк на `~/.ssh`) | ro |

### 9.3. Кейси, які треба тестувати
- ✅ Зміна файлу у Windows Explorer → одразу видно в `cat` Linux.
- ✅ `git status` показує правильний стан після зміни з Windows.
- ✅ Великі бінарні файли (>1 ГБ) — без OOM.
- ✅ Watch-режими: `nodemon`, `vite dev`, `tsc --watch` бачать зміни ззовні.
- ✅ Імена файлів з кирилицею, пробілами, спецсимволами.
- ✅ Long paths (>260 символів) — virtiofs має це підтримувати.
- ✅ Регістрозалежність: NTFS — case-insensitive, треба `noatime,case_sensitive=on` чи аналог.
- ✅ Permissions: chmod з Linux не падає, але реально нічого не змінює (NTFS).
- ⚠️ Hard links — обмежено.
- ⚠️ FIFO/socket-файли — створювати тільки на rootfs, не на спільному.

### 9.4. Edge cases
- Якщо Windows-папка зашифрована BitLocker і не змонтована — мапінг падає з зрозумілою помилкою.
- Якщо файл відкритий ексклюзивно (Word, Excel) — Linux read падає, треба показати hint.

## 10. Мережа та автоматичне прокидання портів

### 10.1. Базова мережа
- QEMU `-netdev user` (SLIRP) → DHCP видає `10.0.2.15` гостю, шлюз `10.0.2.2`.
- Гість має повний доступ в інтернет через NAT хоста.
- DNS: проксіюється з Windows resolver.

### 10.2. Прокидання портів — алгоритм

**Guest Agent (всередині Linux):**
1. Кожні 500 мс читає `/proc/net/tcp`, `/proc/net/tcp6` (швидко, без іптерувань).
2. Виокремлює сокети у стані `LISTEN` (state = 0A).
3. Порівнює з попереднім зрізом: знаходить `added` і `removed` порти.
4. Надсилає JSON через `virtio-serial` контролеру:
   ```json
   {"type":"port_event","action":"added","port":8080,"bind":"0.0.0.0","pid":1234,"comm":"node"}
   ```

**Controller (на Windows):**
1. Отримує подію → відкриває `TcpListener` на `127.0.0.1:8080`.
2. На кожне нове з’єднання — встановлює зв’язок з гостем через `virtio-vsock` або всередину SLIRP-форвардингу та копіює стрім bidir.
3. На `removed` — закриває listener.

### 10.3. Альтернатива: динамічний QMP
QEMU підтримує `hostfwd_add` через монітор. Можна не робити окремий проксі, а керувати SLIRP напряму:
```
hostfwd_add tcp:127.0.0.1:8080-:8080
```
**Перевага:** ядро Linux не бачить різниці (швидше). **Мінус:** обмеження SLIRP (іноді ламається при HTTP/2, gRPC, WebSocket з великими фреймами). Тестувати обидва підходи.

### 10.4. Зворотний напрямок
- Гість резолвить `host.winmux.local` → `10.0.2.2` (хост у SLIRP).
- Усі порти Windows доступні гостю напряму.
- Спецдомен `host.winmux.local` додається в `/etc/hosts` автоматично.

### 10.5. Конфлікти портів
Якщо порт уже зайнятий на хості (наприклад, IIS на 80):
- Не падати, повідомити в UI: "Port 80 conflict with: w3wp.exe — skipping forward".
- Опція: автопереназначення (8080 → 18080).

## 12. Drag-and-Drop: файли, папки, скріншоти, посилання

> Це одна з ключових фіч, яка наближає WinMux до досвіду веб-Claude.

### 12.1. Сценарії
| Що перетягують | Дія |
|----------------|-----|
| Файл з Windows Explorer | Якщо файл у `/workspace` (чи на змонтованій ФС) → вставити шлях у термінал. Якщо ні (наприклад, з `C:\Temp\`) → скопіювати в `<dropdir>/` і вставити шлях |
| Папка | Опція 1: вставити шлях. Опція 2 (через Shift+drop): `cd` у цю папку |
| Зображення з браузера (drag image) | Зберегти в `<dropdir>/img-YYYYMMDD-HHMMSS.png`, вставити шлях |
| Текст / URL | Вставити як текст у позицію курсора |
| Кілька файлів | Вставити список шляхів (space-separated, з лапками для шляхів з пробілами) |
| Скрін з буфера (Ctrl+Shift+V коли image) | Те саме, що drop image |
| Запис з clipboard з форматом FileGroupDescriptor (з Outlook/Teams) | Зберегти, вставити шлях |

### 12.2. Папка для дропів (`<dropdir>`)
**Дефолт:** `$WORKSPACE/.winmux-drops/` (тобто всередині поточного проекту, щоб claude мав доступ).

Альтернативи (налаштовуються в config):
- `~/.winmux-drops/` (глобальна).
- Кастомний шлях.
- `false` — ніколи не копіювати, тільки коли файл уже на спільній ФС.

`.winmux-drops` автоматично додається в `.gitignore` глобально (через `~/.config/git/ignore`).

### 12.3. Інтеграція з Claude
Якщо в активному рядку терміналу вже є слово `claude` (визначається парсингом):
- Drop image → автодоповнюється `--image $path` (або синтаксис, який буде в новому Claude).
- Drop файлу проекту → не змінює, лише вставляє шлях (Claude сам прочитає).

Це опціонально, контролюється через `config.toml`.

### 12.4. Технічна реалізація
- Tauri підтримує DnD events: `tauri::WindowEvent::FileDrop`, `DragEnter`, `DragLeave`.
- Для зображень з буфера/браузера — використовуємо HTML5 DnD API всередині WebView, потім Tauri-команда `save_image_to_drop_dir(bytes)`.
- Збереження в гостьову ФС напряму (через virtiofs) — не треба IPC.

### 12.5. UX-деталі
- Під час drag: показати overlay у вікні з підказкою "Drop file → path will be inserted".
- Після drop: коротка ноттіфікація знизу "Saved as `.winmux-drops/img-...png`, path inserted".
- Конфлікт імен: додавати `-1`, `-2` суфікс автоматично.
- Великі файли (>50 МБ): запитати підтвердження "Copy 350 MB file?".

### 12.6. Edge cases
- Drop у TUI-програму (vim, fzf): не вставляти текстом, а спитати "Save to drops only?".
- Drop коли термінал scrolled up: спочатку прокрутити в кінець.
- Drop на час виконання інтерактивної команди (наприклад, redis-cli): шлях підставиться у поточний ввід.

## 13. Контролер (Host Daemon)

### 13.1. Функції
1. Запуск і нагляд за `qemu-system-x86_64.exe` (restart on crash).
2. Підняття `virtiofsd` для кожної спільної папки.
3. Проксі портів (TCP/UDP) Linux ↔ Windows.
4. IPC сервер (named pipe `\\.\pipe\winmux-<userid>`).
5. Синхронізація буфера обміну.
6. Telemetry відключена за замовчуванням; локальні логи — так.
7. Tray-іконка (опційно), запуск з автозавантаження користувача (НЕ системного).

### 13.2. Lifecycle
- Старт: коли користувач запускає вікно WinMux. Якщо контролер уже працює — підключитися до нього.
- Зупинка: явна команда `winmux quit` або кнопка в tray. Закриття останнього вікна — НЕ зупиняє (за замовч.).

### 13.3. Багатовіконність
Один контролер — N вікон (вкладки можуть бути в різних вікнах, всі підключені до однієї guest VM через різні tmux-сесії).

### 13.4. Хто запускає QEMU
Контролер. QEMU command line формується програмно з шаблону:
```
qemu-system-x86_64.exe ^
  -accel whpx,kernel-irqchip=off (якщо доступно) або -accel tcg (fallback) ^
  -m 2G -smp 4 ^
  -drive file=base.qcow2,if=virtio,readonly=on ^
  -drive file=user.qcow2,if=virtio ^
  -netdev user,id=n0,hostfwd=tcp::2222-:22 ^
  -device virtio-net-pci,netdev=n0 ^
  -chardev socket,path=...,id=fs0 -device vhost-user-fs-pci,queue-size=1024,chardev=fs0,tag=workspace ^
  -chardev socket,id=ctl0,path=\\.\pipe\winmux-ctl ^
  -device virtio-serial -device virtserialport,chardev=ctl0,name=org.winmux.ctl ^
  -nographic -serial mon:stdio
```

## 14. Guest Agent (всередині Linux)

### 14.1. Мова
Rust (статично злінкований з `musl`, ~3 МБ бінарник). Запускається як PID 1 → форкає init у tmux-обгортку.

### 14.2. Завдання
- Монтує virtiofs та `/proc`, `/sys`, `/dev`.
- Налаштовує мережу (`ip addr`, `dhclient` або static).
- Експортує env-змінні з хоста (отримує через IPC при старті).
- Запускає port watcher.
- Запускає clipboard sync.
- Запускає tmux як основну сесію.
- Обробляє команди з хоста: `mount`, `unmount`, `set_env`, `restart_tmux`, `inject_text`.

### 14.3. Bootstrap послідовність
```
1. winmux-init (PID 1)
2. ├─ mount virtiofs /workspace
3. ├─ mount virtiofs /c, /d (за конфігом)
4. ├─ network up (dhclient eth0)
5. ├─ /home/winmux підготовка з overlay
6. ├─ exec /usr/local/bin/winmux-agent
7. │
8. winmux-agent
9. ├─ get env from host via virtio-serial
10. ├─ write ~/.profile з env
11. ├─ start port watcher (background thread)
12. ├─ start clipboard sync (background thread)
13. ├─ start tmux session "main"
14. └─ ready signal → host
```

### 14.4. Конфігурація
`/etc/winmux-agent.toml` всередині гостя — синхронізується з Windows config при старті.

## 15. IPC Host ↔ Guest

### 15.1. Канал
**virtio-serial** — спецдевайс QEMU, доступний у госту як `/dev/virtio-ports/org.winmux.ctl`.
Це швидкий бінарний канал без накладень мережі.

### 15.2. Протокол
JSON-RPC 2.0 (зручний для дебагу) з опційним переходом на MessagePack у v2.

### 15.3. Команди (host → guest)
| Метод | Аргументи | Опис |
|-------|-----------|------|
| `set_env` | `{key, value}` | Експорт env-змінної |
| `set_env_batch` | `{vars: {...}}` | Пакетно |
| `tmux_new` | `{name?}` | Нова tmux-сесія |
| `tmux_attach` | `{name}` | Підключитися (повертає PTY ID) |
| `tmux_list` | — | Список сесій |
| `inject_text` | `{session, text}` | Вставити текст у поточний рядок |
| `clipboard_set` | `{content}` | Оновити буфер |
| `mount_extra` | `{tag, path}` | Динамічне монтування |
| `restart_session` | `{name}` | Рестарт |

### 15.4. Події (guest → host)
| Подія | Дані |
|-------|------|
| `ready` | `{guest_version, kernel}` |
| `port_event` | `{action, port, bind, pid, comm}` |
| `clipboard_request` | `{}` |
| `clipboard_set` | `{content}` |
| `notification` | `{title, body, urgency}` |
| `error` | `{code, message}` |

### 15.5. Транспорт PTY
Окремо від керуючого каналу: для кожного tmux-window — окремий `virtserialport`, який мапиться на PTY гостя (через `socat`/нативно).

## 17. Persistence та session management (tmux)

### 17.1. Базова модель
Кожне відкрите вікно WinMux = клієнт до tmux-сервера всередині guest VM.
- За замовчуванням є `main` сесія.
- Кожна вкладка UI = `tmux-window` всередині `main`.
- Split = `tmux-pane`.

### 17.2. Поведінка при закритті
| Дія | За замовч. | Опція |
|-----|------------|-------|
| Закрити вкладку | Закрити tmux-window | "Detach instead" |
| Закрити вікно | Detach (сесія живе) | "Kill on close" |
| Закрити всі вікна | QEMU продовжує працювати (tray) | "Stop QEMU on last window close" |
| Завершити роботу Windows | Graceful shutdown гостя через ACPI signal | — |

### 17.3. Reattach UI
- Tray-іконка → клік → меню "Open WinMux" → автоматично reattach до головної сесії.
- Якщо є додаткові named-сесії ("build", "ai") — підменю.

### 17.4. Snapshot (P2)
QEMU savevm — миттєвий dump RAM на диск. Дозволяє:
- "Заморозити" стан повністю.
- Холодний старт за <1 с (replay snapshot).
- Опційно: робити snapshot щодоби автоматично.

## 18. Безпека, ізоляція, дозволи

### 18.1. Загальна філософія
Це **НЕ пісочниця для захисту від користувача**. Це інструмент для користувача. Гість має повний доступ до файлів Windows-користувача, який його запустив (через спільну ФС), має доступ в інтернет, прокидує порти на хост.

**Ізоляція рівнозначна тому, що дає процес у Windows**. Жодних додаткових прав агент у гості не отримує.

### 18.2. Що НЕ може зробити агент у гості
- Виконати щось як Windows-Administrator (не може — сам процес QEMU без адмін-прав).
- Зашкодити файлам інших Windows-юзерів (NTFS permissions залишаються).
- Залізти в інші процеси Windows (повна ізоляція user-space).
- Відкрити порт на публічну адресу хоста (всі прокиди — на 127.0.0.1 за замовчуванням; явна опція потрібна для 0.0.0.0).

### 18.3. Що МОЖЕ зробити
- Видалити файли в `/workspace` (= папка проекту Windows).
- Зробити `git push` з прокинутими SSH-ключами.
- Ходити в інтернет.
- Слухати порти 1024+ (на 127.0.0.1 хоста).

### 18.4. Опції додаткової ізоляції (опційно)
- `--read-only-fs` — спільна ФС лише для читання.
- `--no-network` — повне відключення мережі.
- `--no-ssh-keys` — не пробрасувати SSH ключі.
- `--no-env` — не експортувати env vars з Windows.

### 18.5. Reset
- "Reset guest" в UI → видалити overlay `user.qcow2`, створити заново. Файли в `/workspace` НЕ зачіпаються (бо вони на хості).
- "Wipe all" → видалити весь `%LOCALAPPDATA%\WinMux\`.

### 18.6. Зберігання секретів
- API-ключі — у Windows Credential Manager (через `windows-credentials` Rust crate).
- Конфіг-файл — у звичайному виглядаді (без секретів).

## 19. Інсталяція, оновлення, упаковка

### 19.1. Дистрибуція
Один з варіантів (можна мати обидва):
1. **Standalone `.exe` (~80 МБ)** — самодостатній, при першому запуску витягує rootfs. Для більшості юзкейсів.
2. **NSIS/Inno інсталятор** — для корпоративних розгортань (без додавання в PATH, без write у `Program Files`).
3. **Portable ZIP** — для серверних розгортань / роботи з флешки.
4. **Winget / Chocolatey** — пізніше, для популяризації.

### 19.2. Структура встановленого
```
%LOCALAPPDATA%\WinMux\
├── bin\
│   ├── winmux.exe           ← UI
│   ├── winmux-controller.exe ← daemon
│   ├── qemu-system-x86_64.exe
│   ├── virtiofsd.exe
│   └── ...
├── rootfs\
│   ├── base.qcow2           ← read-only базовий образ
│   └── user.qcow2           ← overlay користувача
├── logs\
└── tmp\
```

### 19.3. Оновлення
- **UI/Controller**: класичний автоапдейт через GitHub Releases (Tauri підтримує з коробки).
- **Rootfs**: окремий канал, "Update guest OS" в UI → завантажує новий `base.qcow2`. Overlay користувача переноситься.
- **Guest packages**: всередині — звичайний `apt update && apt upgrade`. Не зачіпає базовий образ (ми в overlay).

### 19.4. Видалення
- `winmux uninstall` АБО видалення папки `%LOCALAPPDATA%\WinMux\` АБО UI-кнопка.
- Зачищає: реєстр (context menu), Credential Manager записи, autostart shortcut.

## 21. Логування, телеметрія, діагностика

### 21.1. Логи
- **Controller**: `%LOCALAPPDATA%\WinMux\logs\controller.log` — JSON-line, ротація 10 МБ × 10 файлів.
- **QEMU stderr**: `logs\qemu.log`.
- **Guest agent**: усередині гостя в `/var/log/winmux-agent.log`, копіюється на хост при `winmux diag`.
- **UI**: `logs\ui.log`.

### 21.2. Telemetry

**Telemetry увімкнена.** Модель — **opt-out з прозорим welcome-екраном** при першому запуску:

> "WinMux збирає анонімну статистику використання та крах-репорти, щоб ми могли його покращувати. Жодних особистих даних, файлів, паролів чи команд не передається.
> [✅ Згоден, надсилати анонімну статистику] [❌ Вимкнути телеметрію]"

Кнопка вимкнення доступна також у Settings → Privacy у будь-який момент.

**Що збирається:**
- **Crash reports**: стектрейс контролера/агента/UI БЕЗ вмісту користувацьких файлів і командної історії.
- **Версії**: WinMux, Windows (тип/build), QEMU, Tauri WebView.
- **Базова конфігурація**: профіль ресурсів (light/default/heavy), тема, мова UI, ширина-висота вікна.
- **Подія старту**: cold start time, warm start time, чи був WHPX доступний, версія rootfs.
- **Подія використання фіч (тільки факт + лічильник)**: кількість відкритих вкладок за сесію, скільки разів використано drag-and-drop, скільки портів проксіювалося, чи використовується tmux persistence, яким AI-CLI користуються (`claude`/`codex`/`ollama`).
- **Анонімний інсталяційний UUID** (генерується локально, не привʼязаний до Windows-юзера/email/MAC).
- **Загальна тривалість роботи** (uptime сесії).

**Що НЕ збирається ніколи (hard rules):**
- Вміст файлів, командна історія, env-змінні, API-ключі.
- Шляхи (тільки факт "відкрита папка", без `C:\Users\...`).
- IP-адреси (бекенд відкидає при прийомі).
- Інформація про інші процеси Windows.
- Дані інших юзерів / network neighbors.

**Бекенд:**
- **Хост:** Pop!_OS your-home-server (домашній сервер автора).
- **Доступ ззовні:** через MikroTik your-public-ip NAT → внутрішній порт. Публічний URL: ймовірно `https://telemetry.winmux.app` (CNAME → DDNS denromvas.website з IP your-public-ip), або одразу `https://winmux.denromvas.website/telemetry`. Конкретний шлях вирішимо при деплої.
- **Стек:** Node.js + Express (як у вже існуючих проектах `/home/dromanyuk/api/`: `art-proxy`, `caption-proxy`, `proxy-claude-ai`, `translate-proxy`, `video-proxy`).
- **Сховище:** SQLite (для PoC) → потім Postgres, якщо потік виросте.
- **Аутентифікація:** Bearer-токен у клієнті (зашитий, не секретний — лише захист від базового spam'у), rate-limit на IP.
- **Repo:** окремий під-проект `winmux-telemetry-server`, теж MIT, опубліковуємо одночасно з відкриттям клієнта.
- **Без хмар:** жодних Sentry/Google Analytics/Microsoft App Center/PostHog cloud.

**Прозорість:**
- Сторінка `winmux.app/telemetry` (буде) з повним списком полів.
- Команда `winmux telemetry --show-payload` — друкує наступний пейлоад, який буде надіслано (для аудиту юзером).
- Локальний кеш не надісланих пейлоадів у `%LOCALAPPDATA%\WinMux\telemetry-queue\` (юзер може видалити).
- Раз на місяць — public dashboard з агрегованою статистикою (топ ОС, топ профілів) — щоб юзери бачили, що саме збирається.

### 21.3. Команда `winmux diag`
Створює архів `winmux-diag-YYYYMMDD-HHMMSS.zip` з:
- усіма логами,
- системною інформацією,
- версією QEMU, контролера, агента,
- конфігом (з вирізаними API-ключами).

### 21.4. Health-check
- `winmux status` → версія, стан QEMU, кількість сесій, активні порти.
- HTTP-ендпоінт на named-pipe для скриптових перевірок.

## Додатки

### A. Альтернативи, які розглянуто і відкинуто

| Альтернатива | Чому відкинуто |
|--------------|----------------|
| **Cygwin / MSYS2** | Не справжній Linux, проблеми з нативними бінарниками |
| **WSL1** | Deprecated, обмежений функціонал |
| **WSL2 + автоматизатор** | Все одно потрібен Hyper-V → права адміна |
| **Docker контейнер як термінал** | Вимагає Docker Desktop, який вимагає WSL2/Hyper-V |
| **Cosmopolitan Libc / Blink** | Цікаво, але незрілий ecosystem, не вистачає npm-сумісності |
| **VirtualBox у user-mode** | Потребує драйверів kernel mode → права адміна |
| **Підняти Linux на іншому фізичному сервері + SSH** | Потребує інфраструктуру, не self-contained |

### B. Натхненники / референси
- **Termux** (Android) — простота і power-user UX.
- **OrbStack** (macOS) — швидкість, ефективність, інтеграція.
- **Lima** (macOS) — архітектурний референс для агента.
- **Wezterm** — референс UX терміналу.
- **Warp** — референс сучасного AI-нативного терміналу (але не Linux).
- **Multipass** (Canonical) — інший підхід VM-management.
